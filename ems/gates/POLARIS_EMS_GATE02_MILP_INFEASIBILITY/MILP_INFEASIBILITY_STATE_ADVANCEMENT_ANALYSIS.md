# POLARIS GATE-02 — MILP INFEASIBILITY STATE ADVANCEMENT ANALYSIS
## ANALYSIS OF STATE ADVANCEMENT SEMANTICS ACROSS OPERATIONAL OPTIONS

---

## 1. FROZEN GOVERNANCE RULE

The authoritative policy boundary governing state advancement on MILP infeasibility is:

```text
MILP_INFEASIBILITY_STATE_ADVANCEMENT = MUST_NOT_OCCUR
```

---

## 2. STATE ADVANCEMENT ANALYSIS BY OPERATIONAL OPTION

### OPTION A — TERMINATE AUTOMATIC OPTIMIZATION
- **`STATE_ADVANCES`**: **NO**
- **Authoritative State**: The last valid `StationState` prior to the infeasibility event remains recorded in EMS memory.
- **Physical vs. Simulated State**:
  - The Digital Twin simulator is **not** stepped.
  - Physical reality continues independently. Physical hardware governors operate according to local control loops.
  - Software state and physical hardware state begin to diverge immediately.

### OPTION B — RETRY / RE-SOLVE OPTIMIZATION
- **`STATE_ADVANCES`**: **NO** (while retry is pending)
- **Authoritative State**: System holds the current `StationState` at time step $k$.
- **Physical vs. Simulated State**:
  - If a retry succeeds within the control interval, state advances under the newly generated feasible plan (`STATE_ADVANCES = YES`).
  - If all retries fail, state advancement remains **NO**, and execution transitions to Option F.

### OPTION C — RELAX CONSTRAINTS
- **`STATE_ADVANCES`**: **YES** (after a relaxed plan is generated)
- **Committed Dispatch**: The dispatch plan generated by the relaxed optimization problem ($k=0$ control action) is dispatched to hardware.
- **Fuel Consumption**: Diesel fuel is consumed based on the relaxed diesel output $P_{\text{diesel}}[0]$.
- **SOC Update**: Battery SOC updates in simulator and hardware according to $P_{\text{battery}}[0]$.
- **Feasibility Guarantee**: Feasibility is guaranteed relative to the *relaxed* constraint set, but requires explicit governance policy defining maximum relaxation limits.

### OPTION D — AUTOMATIC OPTION-D FALLBACK
- **`STATE_ADVANCES`**: **YES** (under Option D emergency plan)
- **Committed Dispatch**: Option D heuristic dispatch action ($k=0$) is dispatched.
- **Fuel Consumption**: Fuel consumed per Option D diesel rule.
- **SOC Update**: Battery SOC updated per Option D battery rule.
- **Feasibility Guarantee**: Option D relies on emergency load shedding to guarantee mathematical feasibility, but is **rejected by governance** for MILP infeasibility events (`NO_AUTOMATIC_OPTION_D_ROUTING`).

### OPTION E — OPERATOR / MANUAL INTERVENTION
- **`STATE_ADVANCES`**: **NO** (automatic) / **YES** (manual operator command)
- **Committed Dispatch**: Dictated by operator input via manual interface.
- **Feasibility Guarantee**: Dependent on operator expertise and manual interlocks. Currently ungoverned and unimplemented.

### OPTION F — REMAIN UNRESOLVED *(SELECTED)*
- **`STATE_ADVANCES`**: **NO**
- **Authoritative State**: The `StationState` remains fixed at step $k$. `DigitalTwinSimulator.step()` is **not** called.
- **Physical vs. Simulated State**: Software simulator state advancement is blocked (`ENGINEERING_INTERFACE_BLOCKER`). Physical station hardware holds previous setpoint or relies on local hardware protection.

## 4. FORENSIC AUDIT OF HISTORICAL RUNNER STATE ADVANCEMENT

In `system/runtime/runner.py` (lines 184–195), pre-existing code exhibited the following state advancement behavior upon receiving `OPTIMIZATION_INFEASIBLE`:

```python
fault_event = FaultEvent(
    timestamp=current_state.timestamp,
    fault_class="OPTIMIZATION_INFEASIBLE",
    severity="GOVERNED_DEGRADED",
    response="GOVERNED_ZERO_DISPATCH",
    state_advanced=True,  # <--- PRE-EXISTING VIOLATION
)
```

### Forensic Breakdown of Pre-Existing Violation
1. `state_advanced=True` was recorded.
2. The runner extracted `action_k0` (0 kW diesel, 0 kW battery power) from the synthetic placeholder plan.
3. The runner invoked `DigitalTwinSimulator.step(action_k0)`.
4. The simulator advanced the `StationState` to $k+1$, simulating a complete power blackout (0 kW served, 100% unmet load).

### Governance Finding
This pre-existing behavior **committed an un-governed zero-dispatch action and advanced state under an infeasible plan**. Under frozen Gate-02 rules, this behavior is non-compliant. `MILP_INFEASIBILITY_STATE_ADVANCEMENT = MUST_NOT_OCCUR` strictly prohibits invoking `DigitalTwinSimulator.step()` or setting `state_advanced=True` on `OPTIMIZATION_INFEASIBLE`.
