## 2. Execution/status call graph — guard detection through final persisted result

**Standalone / single-shot path (`PolarisLocalRunner.run_pipeline`, `runner.py`):**
```
GAP19HighsNativeOptimizer.optimize() → DispatchPlan (unmet_load always set; unmet_essential
   never set in production; reserve_shortfall set by GAP19 and Option D's sibling paths differently)
 → runner.py: constraint_status checked for "OPTIMIZATION_INFEASIBLE" prefix only (:187-200)
   → if infeasible: execution_status = "GOVERNANCE_DECISION_REQUIRED", loop breaks (guard never consulted)
 → simulator.step() (exceptions → FAILED_TERMINATED)
 → EvaluationEngine.evaluate_ems_performance(dispatch_plans, configs)  [evaluator.py:71-308]
     → per-plan: reserve_policy_guard.evaluate_dispatch_safety(...)  [evaluator.py:186-230]
         → hard-SOC violation → caught, converted to dispatch_safety.hard_soc_violation=True (never raises out)
     → returns dict incl. "dispatch_safety": {...}
 → run_report["ems_evaluation"] = ems_eval   (dispatch_safety is a NESTED, READ-ONLY sub-field here)
 → run_report["execution_status"] computed EARLIER, at :294-302, from fault_events ONLY —
   dispatch_safety is never read back into execution_status.
 → json.dump(run_report, .../run_report.json)   ← FINAL PERSISTED RESULT. Can show
   execution_status: "SUCCESS_CLEAN" simultaneously with ems_evaluation.dispatch_safety.
   optimal_but_unsafe_step_count > 0 and/or hard_soc_violation: true.
```

**Campaign/worker path (`CampaignWorker.execute`, `worker.py`):**
```
GAP19HighsNativeOptimizer.optimize() / OptionDFallbackSolver.solve() / ReactiveHybridA2Optimizer.optimize()
 → (Cell B) if constraint_status startswith "OPTIMIZATION_INFEASIBLE": Gate-02 Option C relaxation
     re-solve. If STILL infeasible → status = "BLOCKED_INFEASIBLE"; loop breaks.  ← the ONLY
     safety/solver-derived halt that exists today.
 → worker.py:_evaluate_step_dispatch_safety(plan)  [:99-193]
     → reserve_policy_guard.evaluate_dispatch_safety(...) → ReservePolicyViolation caught locally
       (:147-154), converted into step_safety["hard_soc_violation"]=True. Never raises out of the
       helper; never affects `status`.
 → integrity_counters updated additively (:455-468) — never read to set `status`.
 → per-step record (incl. "safety": step_safety) appended to in-memory `records` list.
 → loop continues to next step k regardless of any safety finding.
 → after loop: safety_summary built from integrity_counters (:533-552, incl. any_safety_finding flag)
 → trajectory_records.json written with {"status": status, ..., "safety_summary": safety_summary,
   "records": [...]}   ← status here is STILL "COMPLETED" even if any_safety_finding is True.
 → execute() returns {"status": status, ..., "safety_summary": safety_summary}
 → worker_cli.py: res = worker.execute(); print(json.dumps(res))  — no try/except.
 → master.py: subprocess polled; exit code 0 → workers_info status "COMPLETED", else
   "FAILED_EXIT_{code}" (:216-225) — but campaign-level run_status (:246) looks ONLY at
   self.interrupted, never at workers_info. CAMPAIGN_STATUS.json can say "COMPLETED" while a
   worker's safety_summary.any_safety_finding is True, or even while a worker CRASHED.
```

**Key structural fact:** the guard's findings are visible at three persisted layers
(`run_report.json` / `trajectory_records.json` / worker result dict), but **no layer above the
guard reads those findings to change `status`/`execution_status`/`run_status`**. This exactly
matches both prior reports' own stated conclusion (N6 report Section 9.1; wiring report Section
8, item 4) — this audit independently re-confirms it from source and additionally finds the two
items above (guard's own `reserve_shortfall` zero-default, and `master.py`'s `run_status` not
reflecting a worker crash) that neither prior report documented.

## 4. Reserve-limit evidence (Policy C)

**Documented requirements found:**
- `system/config/battery.yaml`: `min_soc_pct: 20.0` (hard SOC floor, = `min_e_wh = capacity_wh × 0.20 = 40,000 Wh` at the default `capacity_wh = 200,000 Wh`) — this is the **hard floor**, already enforced by GAP19's own variable bounds and independently re-checked by the guard. It is not itself a "reserve shortfall" tolerance.
- `gap19_highs_native.py:111-146`: the EBR reserve *target* `E_EBR_target[t]` is computed per-step from the critical-load forecast (`ebr_req_wh = (1.0/eta_dis) × w_crit_sum_wh`, a rolling 6-hour lookahead sum per the module's own docstring, `:9`), and the terminal reserve target `E_term_target` must be explicitly configured (`terminal_target_wh`, or `terminal_reserve_model: INITIAL_STATE`/`CAPACITY_RATIO`) or the optimizer raises. These are dynamically computed **targets** that the MILP tries to satisfy exactly (`E_next[t] + s_J2[t] >= E_stage2_target[t] + min_e_wh`, `:298`); `s_J2[t]` (`reserve_shortfall`) is the slack that absorbs any shortfall against that target.
- `reserve_policy_guard.py`'s own docstring (`:14`) references "the existing 15 kWh EBR floor" as something it explicitly does **not** rely on or claim sufficient — this figure was not found hard-coded anywhere in `system/config/` or `gap19_highs_native.py` in this pass; it appears to originate from external audit markdown (outside this task's scoped file list) and was not independently re-derived here.
- No file in `system/config/`, `system/safety/`, or `system/optimization/implementations/` contains a numeric **ceiling on how much shortfall against the target is tolerable** (e.g., "shortfall must not exceed N Wh" or "N% of target"). The EBR/terminal-target formulas define what the system *aims* for; they do not define how far short of that aim is acceptable before the result must be treated as unsafe.

**Proposed interpretation:** None is proposed by this audit. Per the protocol's explicit instruction ("do not manufacture a threshold"), and because no engineering document, test, or config in the inspected scope states a tolerance, **no defensible numeric reserve-shortfall ceiling can yet be proposed.**

**Units/horizon/margins that WOULD need to be specified by the project owner before a ceiling could be authorized:** Wh vs. kWh (the guard enforces Wh via `validate_reserve_units_consistent`); per-step vs. cumulative-over-horizon vs. cumulative-over-campaign; whether the ceiling scales with the EBR target (a percentage) or is a fixed absolute Wh figure; whether it differs for the 6-hour EBR window vs. the 24h terminal target.

**Remaining unknowns:** whether the "15 kWh EBR floor" referenced in the guard's docstring is a project-owner-authorized figure from a source outside this task's scope, or merely a descriptive carry-over from prior audit prose — this was not resolved, and this audit explicitly declines to treat it as authorized without confirmation.
