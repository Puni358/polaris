**Date:** 2026-10-18
**Nature of this document:** Design-and-analysis memo only, continuing directly from `RT01_VERIFIED_ROOT_CAUSE_AND_MILP_CORRECTION_PROPOSAL.md` (Part 4.2, Candidate B). **No code was written or executed. **Explicitly not repeated:** the mip-gap/tolerance hypothesis, the H2 dominance-violation theory, and the step-93 diesel-funded-charging counterfactual (all already falsified/closed — see `RT01_TIGHT_GAP_VERIFICATION_REPORT.md`, `RT01_SEVEN_HOUR_FEASIBILITY_AUDIT_AND_E2E_READINESS_REPORT.md`, and Part 1 of the root-cause report). This memo treats the steps-119–121 shortfall (14,974.11 Wh, bit-identical across all three prior counterfactual runs) as a **structural** gap and designs against that conclusion, not around it.

## 1. Architectural facts this design is built on (verified by direct code reading, not assumed)

1. `system/optimization/implementations/milp.py` is **not** a protected file. `PROTECTED_FILES` (`system/orchestration/manifest.py:10-17`) is exactly: `gap19_highs_native.py`, `option_d.py`, `ecd.py`, `router.py`, `simulator.py`, `runner.py`. `milp.py`, the forecast engines, `station_state.py`, `dispatch_plan.py`, `forecast_bundle.py`, and config YAMLs are not on this list. (The orchestrating task also directs this memo to treat `system/orchestration/worker.py` as read-only even though it is not in `PROTECTED_FILES`; this memo honors that instruction and proposes no change to it.)
2. `runner.py` (protected) drives the governed 168h scenario exactly as: `bundle = forecast_engine.predict(...)` → `assessment, route = router.evaluate_and_route(...)` → `plan = optimizer.optimize(bundle, current_state, configs)` (NORMAL) **or** `option_d_solver.solve(...)` (EMERGENCY) → `current_state = simulator.step(...)`. Because `runner.py` cannot be edited, any new signal reaching `milp.py` must travel through one of its three existing parameters: `forecast_bundle`, `station_state`, or `configs` — no new call or new parameter can be inserted into the loop itself.
3. `StationState` (unprotected, `system/schemas/station_state.py:19-35`) is the **only** thing that persists between receding-horizon calls. Across 168 calls it carries forward exactly: `battery_soc_pct`/`battery_energy_wh`, `diesel_running`/`diesel_hours_running`, `diesel_fuel_remaining_liters`, `last_observed_*`, `timestamp`, and (already defined but currently unused on this path) `operating_mode`, `ebr_target_wh_override`, `terminal_target_wh_override`. There is no other cross-call memory anywhere in the pipeline. Any reservation mechanism's only durable "memory" between calls is therefore the **physical SOC and fuel level it leaves behind** — there is nothing else to bank into.
4. `ForecastBundle` (unprotected, `system/schemas/forecast_bundle.py:68`) **hard-validates `horizon_hours == 24`** in its constructor — the 24h horizon is enforced at the schema level, not only by `milp.py`'s `H = 24` (`milp.py:76`). Extending the per-timestep forecast arrays themselves beyond 24 steps is therefore not a small change; it requires a schema change. However, `ForecastBundle.metadata: Dict[str, Any]` (`forecast_bundle.py:65`) is **free-form and already unvalidated** — a legitimate, zero-schema-change channel for a scalar/short-vector "outlook beyond 24h" signal.
5. **Prior art already exists for exactly this problem, in a protected file, on a different path.** `gap19_highs_native.py` (protected; used by `worker.py`'s Cell B campaign path, not by the RT-01 168h scenario) already implements a governed "Pointwise Maximum Reserve Envelope": a 6-hour-lookahead `E_EBR_target[t]` plus a horizon-end `terminal_target_wh` (`gap19_highs_native.py:111-151`), fed either from config or from `station_state.ebr_target_wh_override` / `station_state.terminal_target_wh_override` — fields that already exist on `StationState` precisely for this purpose but are **never read by `milp.py`** and **never set by `runner.py`** on the RT-01 path. This memo's design reuses this proven pattern's *shape* (externally-supplied reserve target, pointwise-maximum envelope, surfaced `reserve_shortfall`) inside the unprotected `milp.py`, rather than inventing a new mechanism — but it cannot simply "turn the override on," because nothing on the RT-01 path ever sets it, and the override as designed is driven only by information already inside the current 24h window.
6. **Critical constraint on where banking can happen at all:** in the baseline trace, the real NORMAL/MILP route is active only through step 93; from step 94 onward `option_d.py` (protected) governs, using its own `preserved_resource` (BATTERY-vs-DIESEL) choice (`option_d.py:160,173`). Option D can decide *which* already-existing resource to drain first; it cannot *create* margin. Therefore **any banked reservation must be built up strictly before step 93** (while `milp.py` still governs) — once the run falls to EMERGENCY, this design has no further lever, and whatever margin was or wasn't banked by then is what Option D has to work with.

## 2. Candidate designs

### Candidate 1 — Static hard fuel/SOC floor inside `milp.py` (REJECTED)
Subtract a fixed liters/Wh margin from `current_fuel_l` / treat it as unavailable before solving. **Rejected:** mechanically this reduces to "never let diesel fund discretionary battery charging below a floor," which is materially the same class of intervention Part 1's counterfactual already ran and found produces a **bit-identical** steps-119–121 result whether removed once (step 93) or everywhere it occurs across the full 168h run. A hard floor also risks real-demand infeasibility if set aggressively, which would silently reduce reliability unless carefully bounded — a safety risk a soft mechanism avoids by construction.

### Candidate 2 — Full single-shot 168h MILP reformulation, removing `H=24` (REJECTED — out of scope)
Would genuinely see the whole horizon at once, but is campaign-scale: full reformulation of the schema-enforced 24h-horizon assumption threaded through `ForecastBundle`, `milp.py`'s variable layout (currently `H*K=360` vars, would become `168*15=2520+`), and likely the receding-horizon call pattern itself in `runner.py` (protected). This is exactly the prior report's already-excluded Candidate B. **If the candidate below proves insufficient, this is the next escalation, and it requires explicit owner authorization as a separate, larger decision before any design work begins — not a quiet fallback.**

### Candidate 3 — Always-on GAP19-style terminal/EBR target, driven only by the existing 24h window (REJECTED alone, retained as Stage 1 building block)
Port `terminal_target_wh`/`ebr_target_wh`'s *shape* into `milp.py`, but trigger it unconditionally every call from config, with no information beyond the current 24h window. **Rejected as a standalone fix:** at step 93 the forecast window covers hours 93–116 — it does not reach hour 119 at all. A target confined to "always hold more margin, every day" is not targeted at the actual event; it degenerates into a generic standing policy with unclear sizing, continuous opportunity cost (foregone curtailment reduction / flexible-load service on ordinary days), and no evidence it would behave any differently from Candidate 1 in effect size. It is retained below only as the *computational skeleton* (Stage 1) that Candidate 4's genuine trigger (Stage 2) is layered onto.

### Candidate 4 (PREFERRED) — Soft, forecast-outlook-triggered terminal-battery-energy reservation + fuel-conservation preference inside `milp.py`

**Mechanism:**
- **Signal channel:** the (unprotected) forecast engine optionally attaches an `extended_outlook` dict to `ForecastBundle.metadata` — e.g. `{"lookahead_h": N, "projected_min_net_renewable_margin_wh": X, "confidence": c}` — computed with the *same* imperfect persistence/clear-sky methodology `LocalBaselineForecastEngine` already uses (`baseline.py`), extended further out and explicitly uncertainty-discounted (confidence decaying with lookahead distance). This requires **no schema change** (`metadata` is already free-form) and **no protected-file edit**.
- **Inside `milp.py` (unprotected), read defensively** (`getattr(forecast_bundle, "metadata", {}).get("extended_outlook")`, default `None` — fully backward-compatible with every existing test and the rule-based/reactive-A2 optimizers, which never populate it):
  - If present and indicating a deficit within a bounded lookahead (e.g. ≤72h, config-governed), compute a **soft** terminal-battery-energy target `E_term_target` for `E[23]` (the horizon-end state), sized from the signal's magnitude and capped at `max_e_wh`.
  - Add **one new continuous slack variable** `s_term ≥ 0` and objective term `reserve_shortfall_penalty * s_term`, with a new constraint row `E[23] + s_term ≥ E_term_target` (soft: shortfall is *priced*, never forbidden).
  - Add a second slack `s_fuel ≥ 0` and a soft row preferring cumulative diesel use to stay below `current_fuel_l - fuel_reserve_target_l`, priced similarly — the existing **hard** cumulative-fuel-budget row (`milp.py:291-300`, `≤ current_fuel_l`) is left completely untouched.
  - **The existing hard SOC floor (`lb[E]=min_e_wh`, `milp.py:148`) and every other existing constraint row are unmodified.** Both new rows are strictly additive.
- **Stage 1 vs Stage 2:** Stage 1 implements only the `milp.py`-side mechanism with a static, config-driven always-modest target (no forecast-engine change) — smallest possible first prototype, isolates "does soft terminal-energy banking do anything at all" independent of any new forecasting logic. Stage 2 adds the genuine `extended_outlook` trigger. Both stages touch only unprotected files.

## 4. Infeasibility handling rule (strict)

Both new terms are **soft** (slack-variable-penalized, not hard bounds on the reservation targets). The feasible region of the MILP is therefore **identical** to today's: same bus-bar balance, same demand-deficit balance, same hard SOC floor (`lb[E]=min_e_wh`), same hard cumulative-fuel cap (`≤ current_fuel_l`). A trivial all-slack solution always exists whenever today's problem is feasible, so:
- **The reservation mechanism can never, by itself, cause `OPTIMIZATION_INFEASIBLE`.** If the base problem is feasible, so is the augmented one.
- When the reservation target cannot be met without sacrificing demand service, the solver pays the penalty and returns a **nonzero shortfall** — surfaced explicitly as a new `reserve_shortfall`-style field on `DispatchPlan` (mirroring the field GAP19 already exposes and `reserve_policy_guard.py`'s existing visibility pattern), never silently absorbed or hidden.
- **No energy is ever fabricated.** The mechanism only reallocates/schedules real available energy against the same unmodified physical constraints.
- **The hard SOC floor and hard fuel cap are never relaxed, lowered, or bypassed** by this design, at any stage.

## 5. Risks and the one condition that would force escalation

The step-93-governs-until-EMERGENCY structure (§1.6) means the mechanism can only bank margin *before* the run falls to EMERGENCY. If validation shows the banked terminal-SOC margin gets fully redrawn by `option_d.py`'s own (protected) `preserved_resource` logic during steps 94–118 before reaching 119–121, closing the gap would require either a larger reservation target (still in-scope, tunable inside `milp.py`) or changing Option D's own preservation policy — which **is** a protected-file change and would require explicit owner authorization before any further design work, exactly per the directive's boundary. This memo does not assume that escalation is needed; it flags the condition under which it would become necessary.

A second risk: an under-tuned reserve-shortfall penalty could materially change curtailment/renewable-utilization behavior on ordinary (non-deficit) days — tracked explicitly in validation (§6), not assumed benign, since the 75% renewable floor must not regress.

## 6. Minimum prototype scope — exact files

- `system/optimization/implementations/milp.py` (unprotected) — add 2 slack variables, 2 soft constraint rows, corresponding objective terms; read `forecast_bundle.metadata.get("extended_outlook")` defensively; populate a new optional `reserve_shortfall` field on the returned `DispatchPlan`.
- `system/schemas/dispatch_plan.py` (unprotected) — `reserve_shortfall` is already an optional constructor field (used by GAP19 today); no change needed, only populate it from `milp.py`.
- `system/config/optimizer.yaml` (not protected, but a **new behavioral parameter** — flagged for explicit owner sign-off before implementation, consistent with "do not change fuel policy": this adds a new dispatch-preference knob, it does not alter the existing no-refuel budget or SOC-floor values) — new `weights.reserve_shortfall_penalty` and reservation sizing parameters.
- Stage 2 only: `system/forecasting/implementations/baseline.py` (and/or `s81_solar.py`) (unprotected) — compute and attach `metadata["extended_outlook"]`.
- **No changes** to `runner.py`, `router.py`, `ecd.py`, `option_d.py`, `simulator.py`, `gap19_highs_native.py`, `worker.py`, or any governance/decision-register file.

## 7. Validation experiment design (for a future, separately-authorized implementation pass — not run here)

- **Harness:** reuse the exact pattern of `research/rt01_diagnostics/trace_step119_counterfactual.py` — real, unmodified `PolarisLocalRunner.run_pipeline(steps_to_run=168)` on `synthetic_168h_endurance_scenario.json`, instance-method wrapping only, same `HASH_TARGETS` pre/post hash-verification of all 6 `PROTECTED_FILES` + `manifest.py` + config YAMLs + scenario file.
- **Runs:** (a) baseline (today's unmodified `milp.py`); (b) Stage 1 candidate; (c) Stage 2 candidate — each a full, independent 168-step run.
- **Exact metrics compared:** `total_diesel_fuel_liters`, `renewable_utilization_pct` (must not regress below 75%), `system_reliability_pct`, `total_unmet_load_kwh`, **steps-119–121 unmet_kwh specifically** (closing the gap means this hits exactly 0.0 — any nonzero reduction must be reported as partial, not rounded up to "fixed"), first-fuel-exhaustion step, last-NORMAL-before-EMERGENCY step (expected to shift — report, don't suppress), cumulative `reserve_shortfall` across the run, solve time per step (confirm negligible compute-cost increase).
- **Regression tests required before implementation is adopted:** the existing `test_s81_e2e_integration.py` (14 tests) and the 168h closure suite (`test_flexible_load_constraints`, `test_flexible_load_no_double_counting`, `test_per_timestep_conservation_audit`, `test_cumulative_physical_conservation_168h`, `test_long_duration_closed_loop_endurance_168h`) — rerun and compared against current figures, not assumed to pass.
- **New structural tests specific to this candidate:** (1) assert the hard SOC-floor row and the hard cumulative-fuel-cap RHS are byte-identical to today's (never weakened); (2) assert `reserve_shortfall` is always surfaced, never silently zero when the solver actually paid a penalty; (3) a monkeypatch counterfactual, structured exactly like the existing baseline/single-intervention/all-interventions three-tier pattern, toggling the new terms on/off via config, to directly measure the steps-119–121 delta.
- **Kept explicitly separate:** the Candidate A startup-fuel constraint fix (prior report §4.1) is **not** combined with this experiment, uses its own separate tests (already specified in the prior report), and addresses a different, already-confirmed `milp.py` formulation inconsistency unrelated to cross-horizon reservation.

## 8. Recommendation

**Candidate 4 (staged: Stage 1 static skeleton, then Stage 2 forecast-triggered)** is the preferred design: smallest footprint, no protected-file edits, no runner.py changes, reuses GAP19's already-governed reserve-target pattern, structurally cannot cause new infeasibility or SOC-floor/fuel-cap violations, and is the only candidate here not already contradicted by Part 1's counterfactual evidence. It is **not implemented in this pass.** Whether it actually closes the steps-119–121 gap is **unverified** and can only be established by the validation experiment in §7, which requires separate owner authorization to execute. If validation shows the banked margin is consumed by Option D before reaching the deficit window, the next step is Candidate 2 or an Option-D policy change — both of which require explicit owner authorization as described in §2 and §5. RT-01 remains OPEN.
