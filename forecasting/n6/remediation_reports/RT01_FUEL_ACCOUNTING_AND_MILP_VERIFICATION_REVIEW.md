## Question 1 — Reconciling 129.48 L against the 100 L tank / no-refueling policy

**Verified finding: this is a reporting/accounting discrepancy, not a physical-state (energy-conservation or fuel-budget) violation — confirmed by direct source reads, not by trusting the prior report's prose.**

Traced the three places fuel is tracked, independently, from current source:

1. **`system/optimization/implementations/milp.py:291-300`** — the MILP's own cumulative fuel-budget constraint: `sum(marg_fuel_l_wh*dt*p_diesel[t] + base_fuel_l_h*dt*u_diesel[t]) <= current_fuel_l`, where `current_fuel_l` is read fresh from `station_state.diesel_fuel_remaining_liters` at the start of each receding-horizon call (`milp.py:48-50`). **This constraint contains no startup-fuel term.** It is a correct, non-exceedable hard bound on `base + marginal` fuel only.
2. **`system/optimization/implementations/option_d.py:230-233`** (EMERGENCY fallback): `fuel_step = (base_lph + marginal_lpwh*p_diesel) * 1.0; available_fuel = max(0.0, available_fuel - fuel_step)`. Diesel is gated only by `available_fuel > 0` (`option_d.py:162,179,209`) — a **boolean** gate, not a check that `available_fuel >= fuel_step`. So the one step where `available_fuel` crosses zero can dispatch a **full** minimum-run hour (base + marginal fuel, ≥ `min_power_w`=10,000 W per `diesel.yaml`) even though less than that remains, with the deficit silently absorbed by the `max(0.0, ...)` clamp rather than blocked. This is a genuine, small, real boundary-sequencing permissiveness in the **protected** `option_d.py` file — confirmed by direct code read, not assumed.
3. **`system/evaluation/evaluator.py:88-157`** — the reported `total_diesel_fuel_liters` metric: identical `base + marginal` formula, **plus** a startup-fuel surcharge (`startup_fuel_l = startup_cost/fuel_cost_per_l = 15.0/2.50 = 6.0 L`) added every time diesel transitions from off→on (`evaluator.py:151-155`). This term exists **only** in the reporting/evaluation layer — neither `milp.py`'s nor `option_d.py`'s live fuel-feasibility tracking ever deducts it.

**Reconciliation, confirmed by recomputing both formulas against the same 168-step trace (figures from `RT01_ROUND1_STABILIZATION_REPORT.md` §2, cross-checked against the source formulas above):**
- Evaluator-reported total: **129.48 L**
- Same trace, operational-tracking formula (no startup term): **105.48 L** — exactly 129.48 − (4 starts × 6.0 L = 24.0 L)
- 100 L nominal tank budget

So the 29.48 L gap decomposes into two distinct, independently-confirmed causes:
- **~24 L (the dominant share): a pure reporting-layer double standard.** The evaluator counts an engine-start fuel cost that the actual dispatch-feasibility logic in both solvers never charges against the tank. The tank itself, as tracked by `option_d.py`/`milp.py`, never reflects this fuel as spent.
- **~5.48 L (the residual): a genuine, small physical-tracking permissiveness**, from the `max(0.0, available_fuel - fuel_step)` clamp in the protected `option_d.py` file (item 2 above) allowing one minimum-run hour to be dispatched when insufficient fuel remains for it, rather than being blocked outright.

**Conclusion:** the 129.48 L figure does **not** mean 29.48 L of fuel was physically conjured from nothing — no conservation law is violated and no test fails because of it. It means the *reported metric* and the *dispatch-feasibility tracking* use two different, inconsistent fuel-accounting formulas, one of which (option (2)) has a second, much smaller, independent boundary-permissiveness bug layered on top. Both are confirmed directly from source in this review, not merely re-asserted from the prior report.

## Question 2 — The claimed "global 168-hour MILP, 0 Wh unmet, 19.823 L" result

**Verified finding: no such artifact, figure, or named result exists anywhere in this repository.** A repo-wide search (`grep -rn "19.823\|19\.82"` across all `.md`/`.json`, plus a separate search for "0 Wh unmet" / "global ... MILP" / "single-shot" / "full-horizon MILP" combined with "168"/"MILP"/"global") returned **zero** matches in any RT-01 report, the decision register, or any other file in the repository. The only "full-horizon" MILP artifact that exists is `N6_REMEDIATION_REPORTS/RT01_FULL_HORIZON_MILP_DIAGNOSTIC_REPORT.md`, which is a **single 24-hour** solve (step 0 of the 168h scenario, forecast horizon only), not a 168-hour single-shot solve, and reports `res.fun = 14,296.38`, zero diesel, zero unmet over that 24h window — not 19.823 L / 0 Wh over 168h.

**Structural reason no such 168h single-shot artifact can exist without a code change:** `system/optimization/implementations/milp.py:76` hardcodes `H = 24  # Horizon hours`. The optimizer's decision-variable layout, constraint construction, and the cumulative-fuel-budget constraint are all built for exactly 24 timesteps per call; it is a receding-horizon MPC controller, re-invoked once per hour with a fresh 24h forecast window, not a solver capable of ingesting a 168-row forecast and returning one 168-step plan. Producing a genuine single-shot 168-hour global MILP result would require either editing `milp.py` (unprotected, but this is explicitly a horizon/formulation change, i.e. exactly the kind of "optimization campaign" work this task excludes) or hand-building a parallel standalone reimplementation of the full formulation (binaries, startup tracking, cumulative fuel constraint, flexible-load window) at 7× the variable count — a non-trivial reconstruction effort, not a "minimal, targeted check."

**What was done instead (bounded, read-only, arithmetic only — not a re-solve):** using only the real, governed config constants (`diesel.yaml`: `min_power_w=10000`, `base_fuel_consumption_l_per_h=5.0`, `marginal_fuel_consumption_l_per_wh=0.00025`, `startup_cost=15.0`→6.0 L/start) and the exact per-step wind/demand/SOC figures `RT01_ROUND1_STABILIZATION_REPORT.md` §2 already captured for the 3 unmet steps, the minimum diesel fuel a governed-constraint-respecting dispatch would need to zero out all 3 unmet events (steps 119–121) was hand-computed:

| Step | Deficit after wind+residual battery (W) | Forced diesel dispatch (W, ≥ min_power_w once "on") | Fuel this hour (L) |
|---|---|---|---|
| 119 | 10,994.38 (covers the 8,919.43 Wh unmet plus the ~2,075 Wh the battery actually supplied) | 10,994.38 | 5.0 + 10,994.38×0.00025 = 7.75, **+6.0 startup** = 13.75 |
| 120 | 5,105.84 | 10,000 (floor forces this) | 5.0 + 2.5 = 7.50 |
| 121 | 948.84 | 10,000 (floor forces this) | 5.0 + 2.5 = 7.50 |
| **Total** | | | **≈28.75 L** |

This hand-computed figure (**≈28.75 L**, same order of magnitude but **not equal to** the cited 19.823 L) is in the right neighborhood to make the user's cited number *plausible as this kind of calculation*, but it is not a match, and it was derived from a manual arithmetic check, not an actual MILP solve — it should not be treated as a verified reproduction of "19.823 L."

**Determination: insufficient evidence exists to verify the "0 Wh unmet, 19.823 L" claim.** It does not correspond to any artifact, log, or figure found in this repository, and the codebase has no built-in capability to produce a genuine single-shot 168-hour MILP result without a scope-violating code change. This is reported as an **unresolved discrepancy**, not fabricated as verified. If the owner has this figure from a source outside this repository, its provenance (which script, which config snapshot, which exact formulation) needs to be supplied before it can be checked against the governed scenario.

## Question 3 — Are the 3 unmet-load events physically unavoidable, or a consequence of earlier dispatch decisions?

**Verified finding: not unavoidable in an aggregate-energy sense; they are best explained as a consequence of the receding-horizon controller's limited look-ahead and (separately) a confirmed non-optimal dispatch pattern earlier in the run — not proof of true resource scarcity over the full 168 hours.** This is supported by evidence already independently re-confirmed in this review, not a new finding manufactured here:

1. **At the moment of shortfall, the 3 events are correctly classified as local resource exhaustion** (`RT01_ROUND1_STABILIZATION_REPORT.md` §2, independently consistent with the source reads above): diesel fuel is genuinely 0.000 L (both `milp.py`'s and `option_d.py`'s live tracking agree it is exactly zero at that point — not merely reported as zero), the battery is pinned at its hard, never-breached 20% SOC floor, solar is zero (night), and available wind alone is below demand. Given **only** the resources physically present at steps 119–121, the shortfall is real and the floor was correctly never crossed.
2. **But the resource picture over the full 168 hours is not scarce.** The same run curtailed **1,395.90 kWh** of renewable energy as unused surplus (`RT01_ROUND1_STABILIZATION_REPORT.md` §5) — **93× larger** than the 14.97 kWh total unmet. The single 24h full-horizon diagnostic (`RT01_FULL_HORIZON_MILP_DIAGNOSTIC_REPORT.md`) independently measured 285,437.8 Wh of curtailment in just one 24-hour window of the same scenario. There is, in an aggregate-energy sense, far more renewable energy discarded earlier in the horizon than would be needed to cover the night-119 deficit — the problem is a **temporal/storage-reservation** limitation (battery charge-power cap of 50 kW, 95% SOC ceiling, and a receding-horizon controller that only looks 24 hours ahead at a time, i.e. it cannot "see" a shortfall 95+ hours in its future and bank for it) rather than an absence of primary energy over the horizon as a whole.
3. **A separate, independently-confirmed MILP defect exists earlier in the run that is consistent with (though not proven to be the specific cause of) this picture.** `RT01_FULL_HORIZON_MILP_DIAGNOSTIC_REPORT.md` §5 found, by direct arithmetic on the actual returned solution (not a counterfactual re-solve), a genuine zero-downside dominance violation at hour 20 of the step-0 horizon: the solver curtailed renewable energy while *simultaneously* discharging the battery to cover the same demand — a strictly worse choice than using the renewable directly, under the model's own stated cost function, confirmed to recur at 7 of 24 hours in that single window (H2 classification, "supported by direct evidence"). This is a confirmed defect in dispatch efficiency during curtailment-rich, zero-diesel hours — i.e., exactly the kind of earlier-horizon inefficiency that, if corrected, could plausibly have left more battery margin banked ahead of a later low-wind night. **This review did not find, and does not claim, a direct causal link proving this specific defect is what caused the night-119 shortfall** — that would require a counterfactual full-horizon re-solve, which is out of this review's scope — but it is independently-confirmed evidence against "pure physical unavoidability" as the full explanation, consistent with (not identical to) the "earlier dispatch decisions" half of the question.
4. **H1 (legitimate multi-period shifting) was already explicitly tested and rejected as a sufficient explanation** for the step-0 pattern by the prior diagnostic (magnitude test failed ~5×: $7,397 of unexplained excess cost vs. a $1,492 maximum plausible one-time benefit) — reinforcing that what is being observed earlier in the horizon is closer to inefficiency/defect than to deliberate, correctly-reasoned reservation.

**Conclusion:** at the instant of shortfall, the 3 events are genuine and the safety floor was correctly respected — this part of the Round-1 report's classification is confirmed accurate and this review does not dispute it. But "genuinely out of resources at that instant" and "physically unavoidable over the whole 168-hour run" are different claims; the second is **not supported** by the curtailment/dominance evidence above. The honest classification is: **avoidable in principle, given the total energy available over the horizon, but not avoidable by the receding-horizon controller as currently built and scoped** — closing it requires either a cross-horizon reservation redesign or a fix to the confirmed earlier-horizon MILP inefficiency, both of which the next section addresses.

## Question 4 — Could a narrowly-scoped, unprotected-file correction address the demonstrated cause?

**Verified finding: it depends on which "demonstrated cause" is meant — and the two must not be conflated.**

**(a) For the Question 1 accounting discrepancy: yes, a narrow, unprotected-file correction is plausible and well-targeted.** `system/evaluation/evaluator.py` is **not** in `PROTECTED_FILES` (confirmed by direct read of `system/orchestration/manifest.py:10-17`: the 6 entries are `gap19_highs_native.py`, `option_d.py`, `ecd.py`, `router.py`, `simulator.py`, `runner.py` — `evaluator.py` is not among them). A narrow fix confined to `evaluator.py`'s `total_diesel_fuel_liters` computation (either dropping the startup-fuel surcharge to match the live feasibility-tracking formula, or relabeling/splitting the metric so the startup cost is reported as a distinct, clearly-named field rather than folded into a number that implies tank-depletion) was checked against the governed test suite and **does not collide with any existing assertion**: `grep` across `system/tests/*.py` found no test that pins `total_diesel_fuel_liters` to `129.48` for the 168h scenario (the only hardcoded value found, `163.5` at `test_offline_runtime.py:615`, belongs to a different test/scenario entirely), and neither `test_cumulative_physical_conservation_168h` nor `test_long_duration_closed_loop_endurance_168h` references `total_diesel_fuel_liters` at all. This path would not require touching fuel policy, scenario assumptions, or any protected file, and is consistent with the directive's boundaries — **but it was not implemented in this review**, since this review is read-only; it is reported as the smallest defensible next action, pending owner authorization.

**(b) For the Question 3 root cause (the 3 unmet-load events themselves): no narrowly-scoped unprotected-file fix is demonstrated.** The candidate that would actually close the 14.97 kWh gap — a cross-horizon fuel/SOC-reservation redesign of the receding-horizon dispatch logic — was already explicitly identified and explicitly excluded by the Round-1 report's own Section 9 as "a general-optimization-campaign-scale redesign," outside this and the prior round's authorization. The one confirmed, unprotected-file-adjacent defect (`milp.py`'s H2 dominance-violation pattern, `milp.py` is unprotected) is real but has **not been shown to causally connect** to the night-119 shortfall specifically — it was observed during a zero-diesel, curtailment-rich daytime window, and testing whether fixing it (e.g., tightening `mip_rel_gap`) would propagate enough extra battery margin 95+ hours forward to change the outcome at steps 119–121 would itself require a new, multi-step counterfactual re-solve — explicitly flagged by `RT01_FULL_HORIZON_MILP_DIAGNOSTIC_REPORT.md` §7 Item 1 as needing **separate owner authorization**, and explicitly out of this review's read-only, no-rerun scope.

**Conclusion:** a narrow, unprotected-file (`evaluator.py`) correction is available and well-supported for the Q1 reporting inconsistency. No narrow, unprotected-file correction is currently demonstrated to close the Q3 unmet-load gap — both paths that could plausibly do so (cross-horizon reservation redesign; or validating and then fixing the `milp.py` H2 defect) require new owner authorization beyond this review's scope.
