## 1. Executive summary

There is a named, specific, currently-active execution gate — `system/evaluation/replay_harness.py`'s `FactorIsolatedReplayHarness.execute_experiment_a()`/`.execute_experiment_b()`, which **unconditionally raise `CampaignExecutionNotAuthorizedError`** — standing between this repository's existing offline evidence and any actual N6-vs-baseline diesel measurement. That gate was not invoked, edited, or bypassed to produce this document.

Independent of that gate, this pass's read-only inspection surfaced a second, previously under-stated prerequisite: **no multi-origin, N6-integrated dispatch-campaign script exists anywhere in the repository.** The only two executable integrations of `N6SolarForecastEngine` (`run_n6_closed_loop_simulation.py`, `n6_operational_pipeline.py`) are both single-origin (confirmed by FOR-02's targeted audit, register Section 19.4). The existing 123-origin campaign framework (`experiments/exp_three_arm_2024`) runs Arms A/A_FIX/B/C — none of which is N6 or Stage 8.1 (FOR-05, verified). Building an N6-integrated analogue of that campaign harness is engineering work that has not been done and is not itself authorized by this planning pass.

A third prerequisite class is owner/governance decisions that are either now recorded as explicit deferrals (SAF-03, SAF-04, DSL-01's `epsilon_tol` — see `POLARIS_MASTER_DECISION_REGISTER.md` Section 21) or still require external evidence this repository cannot produce (EVID-01, EVID-02, UNC-02).

**Bottom line:** even if campaign-execution authorization were granted today, a valid N6-vs-baseline diesel comparison could not yet run, because the N6-integrated multi-origin candidate arm does not exist, DSL-01's `epsilon_tol` is deliberately unset, and the critical-load baseline both arms would be scored against remains self-labeled synthetic. These are independent blockers, not alternate phrasings of the same one.

Both methods raise **unconditionally** — there is no flag, config value, or environment variable that disables this. `ExperimentBConfig` additionally cannot even be *constructed* without its `authorization_token` field matching a module-level sentinel (`_EXPERIMENT_B_AUTHORIZATION_TOKEN = object()`) that is "deliberately never set to any real/guessable value by this remediation" (module docstring, lines 227–232) — i.e., no code path anywhere in the repository can satisfy it.

**Scope this gate requires to be lifted:** a separate, explicit, dated authorization — from the project owner or governance authority, outside this planning instruction — naming the specific experiment/campaign to be executed, its scope (which arms, which origins, which horizon), and (for Experiment B specifically) a real authorization token value. This instruction's own text is explicit that it does **not** grant that authorization: *"This instruction authorizes recording the specified decisions, preparing the governance package, inspecting existing code/documents, and producing the prerequisite analysis. It does NOT authorize executing a replay or campaign."*

**Existing precedent for what such an authorization record looks like:** `experiments/exp_three_arm_2024/AUTHORIZATION_RECORD.json` (schema v2) is a machine-checked record with distinct `calibration` / `execution_preflight` (`scope: "PREFLIGHT_ONLY"`) / `execution` (`scope: "EXECUTE_EXPERIMENT"`) sections, each requiring a named signer, role (`"project lead"`), ISO-8601 UTC timestamp, and the current package/config manifest hashes; `execution` additionally requires `execute_instruction_ref` naming the project lead's separate explicit execute instruction. **No equivalent signed record exists for `replay_harness.py`** — it has no preflight/execute distinction at all today; it simply raises. Any future authorization to run an N6 comparison would need to either extend `replay_harness.py` with an analogous checked-record mechanism, or be granted and enforced some other explicit way — this document does not recommend which, only notes the precedent exists.

**Current status:** `CampaignExecutionNotAuthorizedError` gate is **active and unmodified**. Status: **NOT AUTHORIZED.**

## 6. What a valid comparison must measure — design notes (not an execution plan)

Per the owner's directive Part 3, a valid future comparison must establish, at minimum:

- **Identical initial conditions, load/demand inputs, weather/renewable inputs, and evaluation horizon** across both arms — already enforced by `replay_harness.py`'s `validate_matched_scenario_pair`/`validate_matched_scenario_set` (Table row 5), provided the future N6 harness is built to construct scenarios through that validator rather than ad hoc.
- **N6 forecasts available only at simulated decision time, no future realized solar or oracle information** — already enforced by `forecast_lineage.reject_if_oracle`, already wired into `ScenarioSpec.__post_init__` (Table row 4); `n6_solar` is already classified `CAUSAL_PROVIDER_NAMES`.
- **Exact existing baseline and candidate configurations with source references and hashes** — the baseline's hashes already exist (`experiments/exp_three_arm_2024/manifests/*.sha256`); the candidate's (N6) model hash now derives from `CANDIDATE_N_MANIFEST.json` (FOR-03, consolidated); a *combined* manifest covering both does not yet exist (Table row 12) and should be assembled as part of any future run's own authorization record, not reconstructed afterward.
- **Diesel consumption in litres for both arms, and absolute/percentage change** — computable by the (not-yet-built) N6 harness using the same metric code the existing three-arm campaign already uses; no new metric engineering needed beyond building the harness itself.
- **Critical unmet load, total unmet load, and existing safety/reliability metrics** — computable today via the already-fixed `evaluator.py`/`worker.py` reporting (SAF-09/SAF-10, `ALREADY_RESOLVED`) and `reserve_policy_guard.py`'s `SafetyEvaluationResult`, against the CL-01 provisional-synthetic 11.6 kW value (Table row 6) — never to be reported as real-station-validated.
- **Per-origin outcomes and aggregate results including adverse cases and uncertainty where supported** — the existing 123-origin framework and `FORECAST_UNCERTAINTY_AUDIT.md`/EVID-03's quantile-envelope methodology both already support this; would need to be applied to the new N6 harness's per-origin output once it exists.
- **Handling of optimizer failures, incomplete runs, missing evidence, and safety violations** — `worker.py`'s `status="FAILED_OPTIMIZATION_EXCEPTION"` and `CampaignMaster.compute_run_status()`'s `"FAILED_WORKER_EXIT"` (SAF-10, already fixed and tested) already provide this; would carry over to a new harness automatically if it reuses the same worker/master infrastructure.
