## 3. Is the metric correction valid, and what does it NOT prove?

**The correction is valid, but is a partial application of the owner's authorized text — not a verbatim one — because of a confirmed schema discrepancy, found and documented per the directive's own instruction rather than guessed around.**

The owner's authorization (echoing the eighteenth pass's drafted diff) described the honest signal as `dispatch_safety.critical_unmet_total_wh == "UNKNOWN_NOT_VERIFIED"`. Direct code trace of `system/evaluation/evaluator.py` (lines ~240–256) and `system/safety/reserve_policy_guard.py` (lines ~290–304), cross-checked against `system/schemas/dispatch_plan.py` (where `unmet_load` is a **required**, non-optional constructor argument), plus one authorized run of the exact test harness, show this literal check is **factually false** for this scenario and **unreachable for any production optimizer today**:

- `critical_unmet_total_wh` reads the literal string `"UNKNOWN_NOT_VERIFIED"` only when *no* plan carries `unmet_essential` **and** *no* plan carries `unmet_load`. Since `unmet_load` is required on every schema-valid `DispatchPlan`, that branch can never trigger in production.
- In the actual, reachable case — neither `GAP19HighsNativeOptimizer` nor `OptionDFallbackSolver` ever sets `unmet_essential` — `critical_unmet_total_wh` is instead a **number**: empirically `553842.6` Wh on this scenario (the same mislabeled fallback total, merely relocated under `dispatch_safety`).
- The literal string `"UNKNOWN_NOT_VERIFIED"` *does* appear in this run — but on the semantically **different** `reserve_shortfall_total_wh` field (a reserve-policy-shortfall metric, not critical-unmet-load). Substituting that field for `critical_unmet_total_wh` would itself be a guessed, incorrect mapping between two different metrics.

This also **corrects a claim carried forward, unverified, from the seventeenth pass** (register §33.3, restated in the eighteenth pass's own proposed diff) that `critical_unmet_total_wh` reads `"UNKNOWN_NOT_VERIFIED"` for production-optimizer runs — that claim was apparently never independently executed before this pass, and is now shown incorrect by direct empirical run.

**What was applied instead:** only the schema-confirmed half of the owner's intent — `critical_unmet_source` honestly identifying the fallback (`"FALLBACK_TO_TOTAL_UNMET_LOAD: ..."`, confirmed true both by code trace and by the actual run) — plus the unchanged `renewable_utilization_pct >= 75.0` floor. No assertion equating `critical_unmet_total_wh` to any specific value (string or number) was added, since any such assertion would either be false (the string) or a newly-invented numeric threshold (forbidden).

**What this fix proves:** the test no longer silently asserts that critical-load-specific unmet energy is zero; it now honestly requires the metric's own source label to disclose that it is a total-unmet-load fallback, not a verified critical-specific figure.

**What this fix does NOT prove:**
- It does **not** prove critical-load reliability has been achieved or measured. No production optimizer currently emits `unmet_essential`, so critical-specific unmet energy remains genuinely unmeasured, not zero and not "verified."
- `renewable_utilization_pct >= 75.0` is a resource-usage ratio, not a bus-bar/energy-balance residual — it does not by itself demonstrate physical conservation. (Independent conservation-residual checks live in the separate `test_per_timestep_conservation_audit`, untouched this pass, which already passes.)
- The corrected test's continuing failure (69.37% < 75.0%) is a **newly-surfaced, genuine** finding, not a side effect of this pass's edit: it was always true of the current pipeline, previously masked because the old `assertEqual(... , 0.0)` raised first and the test never reached the renewable-utilization line. It is tied to the same Task-2 root cause (eighteenth pass, §34.2): 167 of 168 steps route to `EMERGENCY`/`OptionDFallbackSolver` after diesel exhausts at hour ~45, and that fallback dispatch mode uses markedly less renewable energy than normal GAP19 dispatch would.
